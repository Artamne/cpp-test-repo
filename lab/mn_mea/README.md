# MN-MEA: отдельная реализация и стенд проверки

Задание T-186. Алгоритм MN-MEA по главе 5 книги «无人机高机动条件下 SAR 成像»,
разобранной в документе `MN_MEA_Algorithm_Book_RU.pdf`. Документ —
**единственный источник формул**; здесь нет ни одной формулы, которой нет там.

Это **отдельный код**: в `packages/` не тронуто ни строки. Встраивание —
отдельное задание, если владелец решит.

Код написан так, чтобы его читали, положив рядом документ: структура файлов
повторяет структуру документа, каждая функция в докстроке называет номер
формулы, которую реализует, порядок функций в файле — порядок выполнения.

## Как запустить

```
python3 bench/run.py            # всё: опыты, графики в ./out, отчёт ./out/report.md
python3 bench/run.py /путь/куда # то же, в другой каталог
```

**Пока возитесь — пишите в СВОЙ каталог, не в `./out`.** Содержимое `./out`
лежит в репозитории: это отчёт и графики того прогона, что соответствует
коду. Запуск без аргумента их перезаписывает, и `git pull` потом отказывает —

```
error: Your local changes to the following files would be overwritten by merge:
    lab/mn_mea/out/report.md
```

Поэтому:

```
python3 run.py ~/mnmea-out          # Linux
python run.py E:\temp\mnmea-out     # Windows
```

А если уже перезаписали и `pull` встал — выбросить своё и потянуть заново
(файлы генерируемые, терять нечего):

```
git checkout -- lab/mn_mea/out/
git pull origin claude/determined-clarke-e3hdlk
```

Нужны `numpy` и `matplotlib`, они перечислены в `requirements.txt`:

```
python3 -m venv .venv
source .venv/bin/activate
pip install -r lab/mn_mea/requirements.txt
```

Видеокарта необязательна: есть `cupy` — считаем на ней, нет — на процессоре.
`uv run` и `uv sync` не используются (правило 21).

Код возвращает 0, если все проверяемые замером пункты приёмки §10 выполнены,
и 1 иначе.

## Главное, что нужно знать про этот алгоритм

Замерено на 12 сценах, отличается только зерно генератора. Числа — в отчёте,
раздел 1а.

**Минимум энтропии не лежит в истинной точке.** Энтропия (5-6) посчитана в
трёх местах: при нулевой фазе, при ИСТИННОЙ и при найденной. Во всех 12
случаях из 12 `S(найдено) < S(истина)`, медианный зазор 0,131. То есть
итерации отрабатывают верно — они и должны идти в минимум, — но минимум
находится не там, где истина. У фазы `M` свободных параметров, и энтропию
всегда можно опустить ниже истинной, стянув энергию в меньшее число
пикселей.

**Отсюда разброс «главного числа».** Остаточная ошибка фазы по 12 сценам:
медиана **0,458 рад**, от 0,049 до 0,746 — разброс в **15 раз**. Сцена,
на которой считается пункт 1 приёмки (0,059 рад), — одна из удачных, и
читать её как типичную нельзя.

**Контраст выходит ВЫШЕ идеального** — медиана 113 % от того, что даёт
истинная фаза, в худшем случае 376 %. Практическое следствие для реальной
записи: **рост контраста сам по себе не доказывает, что фаза найдена
верно.** Он доказывает только, что картинка стала концентрированнее, — а
это и есть то, что минимизируется.

Что замерено и НЕ помогает:

| пробовали | результат |
|---|---|
| больше стробов дальности (16 → 4096) | остаток держится около 0,62 рад |
| мельче нарезка по азимуту (1 → 32 блока) | остаток растёт 0,54 → 0,88, контраст уходит от идеала 121 % → 159 % |
| решение №7 (пустые бины) | чинит сходимость, точность не меняет |
| решение №8 (лучшая точка) | остаток лучше на 3–4 %, не больше |

Это свойство критерия (5-6), а не дефект реализации: формулы книги
воспроизведены как есть, и улучшать их задание запрещает. Записано, чтобы
числа читались правильно.

## Раскладка: где алгоритм, где стенд

```
algorithm/          то, что снимается на реальные данные
    backend.py          выбор GPU/CPU, оба ядра ПФ, счётчики
    stage_a_blocks.py   разбиение на блоки       (5-20)…(5-26)
    stage_b_initial.py  начальная фаза           (4-83),(4-84),(5-27)…(5-30)
    stage_c_iterate.py  итерации MN-MEA          §5.8, девять шагов
    stage_d_assemble.py сборка и окно            (5-3),(5-26)
    inputs.py           договор о входных данных и его проверка

bench/              то, что остаётся здесь
    synthetic.py        СИМУЛЯЦИЯ: сцена, вносимая ошибка, построение h
    validate.py         опыты §7 и §10
    plots.py            графики
    run.py              прогон целиком, отчёт, приёмка
    prepare_slice_rda.py  срез записи из rda@*.h5: h_srez.npy + meta.json
    run_real.py         прогон на этом срезе
    playground.py       песочница для разглядывания данных
```

Граница не декоративная, она проверяема: **ни один файл в `algorithm/` не
импортирует ничего из `bench/`.** Зависимости внутри алгоритма такие:

```
backend  ←  stage_c, stage_d, (synthetic)
stage_a  ←  stage_b, stage_d
```

То есть `algorithm/` копируется в приложение как есть, вместе с `backend.py`,
и ему нужен только `numpy` (или `cupy`). `matplotlib` нужен лишь стенду.

## Что нужно на входе

Полный перечень с единицами, проверками и наименьшим рабочим примером —
отдельным файлом: **[`input_data.md`](input_data.md)**. Там же замерено, что
делать, если ИНС нет. Коротко:

**Обязательное — одно.** Массив `h(k,n)`, комплексный, размера `M × N`:

* `k` — доплеровский бин, он же номер импульса в апертуре, `M` штук;
* `n` — строб дальности, `N` штук;
* раскладка по `k` — как у `numpy.fft`: нулевая частота в индексе 0,
  положительные дальше, отрицательные с конца.

Это данные ПОСЛЕ сжатия по дальности, исправления миграции по дальности и
прямого ПФ по азимуту — ровно то, что стоит входом в блок-схеме §7 документа.
Сам алгоритм ни сжатия, ни миграции не делает.

**Имея только `h`, уже можно работать:** этапы C и D параметров движения не
требуют вовсе. Получится один блок на всю сцену, то есть поправка одна на
всю местность. Для неманёвренного носителя или небольшой сцены этого хватает.

**Параметры движения нужны только этапам A и B** — тем, что делят сцену на
блоки и дают начальную фазу. Это `Geometry`, пятнадцать обязательных чисел и
одно необязательное:

| поле | что это | откуда брать |
|---|---|---|
| `v_x0, v_y0, v_z0` | скорость носителя, м/с, три оси | ИНС/GPS на момент середины апертуры |
| `a_x, a_y, a_z` | ускорение, м/с² | оттуда же |
| `x_m, y_m, z_m` | координаты центра сцены относительно носителя, м | геопривязка |
| `R_B0` | наклонная дальность до центра сцены, м | из геометрии съёмки |
| `lambda_` | длина волны, м | паспорт станции |
| `f_0` | несущая, Гц | паспорт станции |
| `r_a` | РАЗРЕШЕНИЕ по азимуту (ширина отклика), м | паспорт обработки |
| `r_b` | разрешение по дальности, м/отсчёт | паспорт обработки |
| `T_a` | время синтеза, с | паспорт обработки |
| `r_a_step` | ШАГ картинки по азимуту, м/отсчёт; можно не задавать | `v/PRF` |

Последние два по азимуту — **разные числа**, и путать их дорого. `r_a` входит
в критерий (5-20) `|ΔR| ≤ r_a/2` — про ширину отклика. `r_a_step` входит в
перевод (5-22) `m_p = 2·x_p/шаг` — про число отсчётов в блоке. На реальной
записи шаг обычно в 1,2–1,5 раза мельче разрешения, и одно число на обе роли
ошибается в размере блока ровно во столько же раз. Не задан `r_a_step` —
берётся `r_a`, что верно для критично дискретизованной картинки.

Точности от них нужно немного: они задают РАЗМЕР блока (5-20) и стартовую
точку (5-30), а не сам ответ — ответ ищут итерации этапа C. Ошибка в
параметрах движения ухудшает сходимость, но не портит найденную фазу.

**Чего НЕ нужно:** истинной фазовой ошибки (её на записи никто не знает —
она и есть то, что ищется), опорной сфокусированной картинки, разметки целей.
Всё это есть только на стенде, и потому стенд лежит отдельно.

### Прогон на реальной записи

Два шага, и в каждом данные выбираются по-своему.

**Шаг 1, подготовка среза.** Делается скриптом `bench/prepare_slice_rda.py`
на машине, где лежит запись. Аргумент один — путь к файлу этапа `az`:

```
python bench\prepare_slice_rda.py "D:\test1\results\src-0454fb28e3_rda@4ec41d.h5"
```

Больше вводить нечего: скорость (`..\cache\src-<тот же id>_vel@*.npz`) и
паспорт съёмки (группа `params` внутри того же `.h5`) скрипт находит сам по
идентификатору источника в имени файла.

Вход — именно `rda`, а не `rcmc`. В `rcmc` азимут ещё не сжат, и остаточная
фаза там не единицы радиан, а вся азимутальная ЛЧМ целиком: цель при φ = 0
размазана шире своего блока, и MN-MEA такое не вытянет. В `rda` изображение
уже построено, осталась только та фаза, которую прямолинейная модель снять
не смогла, — её алгоритм и ищет.

Кладёт результат рядом с `.h5`, в `mn_mea_srez\`: `h_srez.npy`, `meta.json`,
`srez.png`. Нужен `h5py` — в `requirements.txt` он закомментирован, это
зависимость подготовки, а не алгоритма.

**Где встаёт срез по азимуту.** Сначала пробуется центр согласных ячеек
матрицы скорости. Но её `az_bin` индексирует ПОЛНУЮ запись, а `rda`-файл —
её кусок, и смещения куска в паспорте нет: на второй записи владельца
`az_bin` доходил до 62480 при 4608 импульсах в кадре. Тогда окно упиралось
в край, срез вставал в хвост кадра, и фокусировать было нечего — контраст
2,88 → 2,89 и девять блоков, сошедшихся за 1–2 итерации. Поэтому индекс вне
кадра означает постановку **по энергии**, туда, где на кадре есть сцена;
индекс внутри кадра берётся как есть, но энергия его окна всё равно
сравнивается с лучшей и печатается.

**Контраст меряется в долях спекла.** У однородного полностью развитого
спекла контраст ровно `√2 ≈ 1,41` — это не подгонка, а следствие
экспоненциального распределения интенсивности. Прогон печатает «над
спеклом» и предупреждает, если контраст ДО автофокуса ниже `2√2`: на таком
срезе выраженных отражателей нет и энтропийному критерию не за что
зацепиться. Для сравнения: первая запись владельца дала 22,40 — это 15,8
спекла; вторая 2,88 — 2,0 спекла.

**Шаг 2, прогон.** `run_real.py` файл не выбирает вовсе: ему даётся
**каталог** `mn_mea_srez` целиком, имена внутри фиксированы.

```
python3 bench/run_real.py путь/к/mn_mea_srez           # сетка блоков по (5-20)
python3 bench/run_real.py путь/к/mn_mea_srez 8x1       # сетка рукой
python3 bench/run_real.py путь/к/mn_mea_srez 8x1 0.01  # и порог (5-9)
```

Порог останова на записи — `MU_REAL = 0,03`, а не стендовый `1e-3`. Это
замер, а не вкус: на срезе 457x200 при `1e-3` уходит 40 итераций и все блоки
докладывают «не сошлось», при 0,03 — 12 итераций и сходятся все, а энтропия
отличается на три сотых процента.

На Windows — из каталога `lab\mn_mea` клона, с включённым venv:

```
.venv\Scripts\activate
cd путь\к\клону\lab\mn_mea
python bench\run_real.py E:\Work\__Galogram__\cluade\RSA_MAX\mn_mea_srez
```

Печатает замечания по входу (`inputs.check_inputs`), числа, которые даёт
геометрия, таблицу по блокам и контраст с энтропией до и после; рядом со
срезом кладёт `mn_mea_do_posle.png`. Книжный этап B не делается — на записи
без ИНС книжная (5-30) мешает, см. «Если ИНС нет» в
[`input_data.md`](input_data.md). **Вместо него идёт этап B без ИНС**
(решение №10, `algorithm/stage_b_search.py`): начальная фаза ищется как
полином по энтропии всей сцены, и этап C стартует из неё. Это включено по
умолчанию; `start=nol` — этап C из нуля, как было. Из нуля на настоящей
записи не работает, и это замерено, см. решение №10.

**Чего этот прогон сказать НЕ может — что фаза найдена верно.** Истины на
записи нет ни у кого, и никакое число её не заменит. Энтропия обязана упасть:
алгоритм её и минимизирует, это цель, а не проверка. Независимо смотрят
контраст и глаза. Единственная объективная сверка, какая тут возможна, —
нарезка: если в паспорте есть раздел `ozhidaemaya_narezka`, `run_real.py`
сличает с ним свой размер блока и число блоков по дальности и печатает
«сходится» или «НЕ СХОДИТСЯ».

## Видеокарта и процессор

Выбор — в одном месте, `backend.py`. Остальные файлы про `cupy`/`numpy` не
знают: они получают объект `Backend` и работают его методами.

Накопление сумм по M·N ячейкам — **всегда в двойной точности**, независимо
от того, в чём лежит массив: в `E_g = −Σ|g|² ln|g|²` десятки тысяч слагаемых.

Сверка двух бэкендов обязательна и делается в `validate.experiment_backends`;
названное число расхождения — в отчёте. На машине без видеокарты сверяются
два пути процессора, двойная и одинарная точность; отчёт говорит об этом прямо.

# Решения реализации

Четыре места, где книга молчит, — и ещё два, найденные уже в работе. Каждое
решено явно, и каждое подтверждено
замером в отчёте, а не мнением.

## Решение реализации №1: нули в логарифме

**Задача.** `ln|g|²` при `|g| = 0` — минус бесконечность, а `|g|² ln|g|²`
даёт `nan`. То же в `L = 1 + ln P` (5-14) и в `W_n(n) = Σ_m (2 + ln P)` (5-19).

**Правило.** Мощность под логарифмом не опускается ниже порога

```
P_порог = 1e-12 · S_g / (M·N)
```

то есть 1e-12 от **средней мощности изображения**, или −120 дБ от неё.
`S_g` — полная энергия (5-4); она от φ не зависит (§5.2 документа), берётся по
равенству Парсеваля прямо из `h` и потому постоянна на все итерации блока.

**Почему так, а не абсолютная эпсилон-затычка.** Три причины, все проверяемые:

1. Порог **относительный**, поэтому он не ломает независимость шага от
   нормировки ПФ (решение №3): при `g → αg` и порог, и мощность
   умножаются на `α²`. Абсолютная эпсилон сломала бы это.
2. −120 дБ от средней мощности заведомо ниже динамического диапазона любой
   реальной записи, поэтому **на измеренных данных порог не срабатывает
   никогда**. Срабатывает он только на синтетике с точными алгебраическими
   нулями, которых в измеренных данных не бывает.
3. Доля пикселей, попавших на порог, **всегда попадает в отчёт** — правило
   не молчит.

**Чем подтверждено.** График `08_power_floor_effect.png` и таблица в отчёте:
порог перебирается от 1e-16 до 1e-2 на двух сценах. На сцене с фоном (нулей
нет) выбор не влияет ни на энтропию, ни на результат вовсе. На сцене из
чистых точек (4090 точных нулей из 4096) выбор влияет и на энтропию, и на
остаточную ошибку, — и это единственное место, где он вообще виден.

## Решение реализации №2: нулевая или отрицательная вторая производная

**Задача.** Ньютон (5-8) делит на `E''`. Книга сторожа не даёт. Это не
редкий угол: на сцене без точечных целей (5-19) даёт `E'' ≤ 0` больше чем в
половине бинов — измерено, см. отчёт.

**Правило.** Два названных ограничения, оба попадают в отчёт:

* **`E'' ≤ 0` — бин не обновляется на этой итерации** (политика `freeze`,
  по умолчанию). Квадратичная модель в таком бине минимума не имеет, и
  `−E'/E''` указывает **вверх** по энтропии. Число таких случаев считается и
  печатается. Если `E'' ≤ 0` во **всех** бинах — прогон останавливается с
  причиной «двигаться некуда, это НЕ сходимость».
* **Шаг ограничен по модулю числом 1 рад.** Ограничение ловит случай
  `E'' → +0`, где Ньютон выдал бы огромный шаг. Число выбрано **замером**
  (`validate.experiment_step_limit`, таблица в отчёте), и здесь стоит
  сказать, чем было раньше и почему это было неверно.

  Сначала стояло `π`, с доводом: §5.7 говорит, что фаза определена с
  точностью до 2π, значит шаг больше π новых сведений не несёт. Довод верен,
  а следствие из него — нет. У предела есть второе свойство, решающее:
  критерий останова (5-9) для шага `d` равен `2|sin(d/2)|`, и при `d = π` он
  равен **2** — ровно максимуму, какой (5-9) вообще принимает. Бин,
  упирающийся в предел `π`, держит критерий на 2 навсегда, и (5-9) не может
  выполниться **никогда**: это предельный цикл, а не сходимость. Предел
  обязан быть строго меньше π.

  Замер по всем блокам полного прогона:

  | предел шага | сошлось | итераций (ср.) | остаток (ср.) | критерий = 2, раз |
  |---:|---|---:|---:|---:|
  | π (прежнее) | 2/12 | 33,7 | 0,5981 | **71** |
  | 1,5 | 9/12 | 20,9 | 0,3620 | 0 |
  | **1,0** | **9/12** | 22,1 | **0,3481** | 0 |
  | 0,3 | 8/12 | 23,5 | 0,3275 | 0 |
  | 0,05 | 4/12 | 37,4 | 0,2970 | 0 |
  | 0,02 | 0/12 | 40,0 | 0,3214 | 0 |

Есть вторая политика, `raise`: **отказ с причиной**, с перечислением номеров
бинов. Она показана в отчёте на той же сцене. Молчаливого огромного шага не
делается ни при какой политике.

## Решение реализации №5: снятие сдвига блока перед укладкой

Это решение в перечень задания не входит — оно найдено при разборе готовых
картинок, когда стало видно, что цель уезжает за край блока и выходит с
другой стороны.

**Задача.** Энтропия (5-5) слепа к линейной по `k` фазе: та лишь **сдвигает**
картинку по азимуту, не меняя ни одного `|g|`. Значит алгоритм линейную часть
не определяет и определить не может — каждый блок приходит со своим
произвольным сдвигом. Пока блок смотрят по отдельности, это безразлично. Но
(5-26) укладывает блоки в общую мозаику, и там разнобой сдвигов — это
разъехавшаяся карта: замерено от −7 до +6 отсчёта между блоками одной сцены,
то есть свыше 5 метров при `r_a = 0,4` м. В книге шага нет: §6 говорит только
«блоки укладываются на свои места».

**Правило.** Перед (5-3) с найденным `φ̂` из него снимается линейная часть,
отвечающая сдвигу картинки. Сдвиг находится так:

```
F(m) = Σ_k e^{jφ̂_k} e^{−j2πkm/M}      это (5-3) от одной экспоненты
s    = argmax |F|                      положение пика
φ̂   ← φ̂ − 2πk·s/M
```

Почему именно так. Подставим `φ̂` в (5-3) и вынесем множитель: изображение с
поправкой есть изображение при `φ = 0`, **свёрнутое** с `F`. А `F` — это
отклик блока на точечную цель. Где у него пик, туда вся картинка и переехала.

Опорная картинка при этом **не нужна**: `F` считается из одной только фазы.
Поэтому способ работает и на блоках, где точечных целей нет и цепляться
взаимной корреляции не за что. Стоит одно БПФ длины `M` на блок, вне цикла
итераций, — §10.6 «два БПФ на итерацию» не задевает.

**Сдвиг берётся целый**, и это существенно: к целому сдвигу энтропия слепа
**точно** (замер: разница по (5-6) от 0 до 3e−15), а к дробному — лишь
приблизительно. Поправка обязана быть бесплатной, иначе она меняла бы то, что
алгоритм минимизирует.

**Замер** (`validate.experiment_image_shift`, 3 сцены × 2 вида ошибки):

| (5-26) | блоков с целями на своём месте | средний сдвиг | худший | `S` среднее |
|---|---:|---:|---:|---:|
| без снятия | 29,2 % | 2,17 отсчёта | 7 | 3,8658 |
| **со снятием** | **75,0 %** | **0,50 отсчёта** | **2** | 3,8658 |

Энтропия совпадает до знака — поправка бесплатна, как и задумано.

**Способ не идеален, и выдавать его за идеальный нельзя.** На более широком
замере (5 сцен × 3 вида ошибки, 114 блоков с целями): на своём месте было
24,6 %, стало 48,2 %; средний сдвиг 2,61 → 0,57 отсчёта, худший 9 → 2. У
**15 блоков из 114 стало хуже**, чем было. Причина: `φ̂` не есть в точности
«прямая плюс малый остаток», у `F` пик размыт, и его положение — оценка
грубая. На блоках без единой точечной цели `φ̂` вообще не сходится, и сдвиг у
них смысла не имеет ни до, ни после.

## Решение реализации №6: окно блока с перехлёстом и нулями

Тоже не из перечня задания: предложено владельцем, когда стало видно, как
цель переезжает через край блока.

**Задача.** Книга режет сцену на плитки **встык** (5-24)/(5-25). Отсюда две
беды, обе замеренные:

* расфокусированная цель размазана **шире** своей плитки. Вырезая плитку
  встык, её хвосты просто теряют — замерено, что окно удерживает от 94 % до
  163 % истинной энергии блока: у одних недобор, у других налезло чужое;
* свёртка в (5-3) **круговая**. Содержимое, уехавшее за верхний край,
  выходит снизу и накладывается само на себя.

**Правило.** Для счёта берётся окно шире плитки:

```
перехлёст  0,25·m_b строк соседей с каждой стороны
нули       0,25·m_b нулей с каждой стороны
длина (5-3)  L = m_b + 2·0,25·m_b + 2·0,25·m_b = 2·m_b
```

(Доли менялись трижды, и все три раза по замеру: 0,5/0,5 на первом
стенде, 0,0/0,25 на изменчивом стенде, 0,25/0,25 на настоящей записи —
история ниже.)

Обратно в мозаику идёт **только сердцевина**, ровно `m_b` строк. Поэтому
укладка (5-26) остаётся точной плиткой без нахлёста: перехлёст нужен внутри
счёта, а не в ответе, и требование «блоки покрывают сцену ровно» не
нарушается.

**Замер и ПЕРЕСМОТР.** Сначала доли были подобраны на стенде, где вносимая
ошибка одна на всю сцену. Там выигрывало 0,5 / 0,5. Но такой стенд цену
перехлёста показать не мог **в принципе**: перехлёст тем и плох, что
захватывает землю, где поправка ДРУГАЯ, — а другой поправки в тех данных не
было. Это не мелочь: я выбрал число по замеру, который не мог его опровергнуть.

На изменчивом стенде (`experiment_space_variant_run`, тот же прогон, но
ошибка по (5-27) своя в каждой точке местности) картина другая:

| перехлёст | нули | сошлось | остаток, рад | контраст | пик |
|---:|---:|---|---:|---:|---:|
| 0,00 — как в книге | 0,00 | 4,0/12 | 0,7361 | **34,32** | 100,9 |
| 0,00 | 0,50 | 2,5/12 | 0,7669 | 33,17 | 100,9 |
| 0,00 | 1,00 | 2,0/12 | 0,8482 | 29,77 | 100,8 |
| **0,25 — взято** | **0,25** | 4,5/12 | **0,5889** | 33,92 | 101,0 |
| 0,25 | 0,50 | 5,0/12 | 0,6220 | 33,35 | 101,0 |
| 0,50 — было раньше | 0,50 | 5,0/12 | 0,6014 | 31,27 | 100,9 |

Взято 0,25 / 0,25: лучший остаток фазы при контрасте в пределах 1,2 % от
наилучшего. Прежние 0,5 / 0,5 дают контраст 31,27 против 34,32 — заметно
хуже книжной нарезки встык.

Нули на изменчивом стенде тоже ведут себя иначе: там они контраст **роняют**
(33,17 против 34,32). Объяснение напрашивается такое: лишние нули удлиняют
доплеровскую ось, то есть дают вектору фазы вдвое больше свободы, и она уходит
на подгонку под спекл. Как объяснение это **не проверено** — проверен только
сам факт.

**Цена.** Длина (5-3) выросла втрое, значит и оба азимутальных БПФ итерации
втрое длиннее. Число БПФ на итерацию не изменилось: их по-прежнему два,
счётчик в отчёте это подтверждает.

**ОТМЕНЕНО ЧАСТИЧНО, замером на настоящей записи: маска сердцевины в
критерий больше не идёт.** «Перехлёст без права голоса» делался маской: (5-5),
(5-14) и первый член (5-19) суммировались только по строкам сердцевины, а
`S_g` (5-4) оставалась энергией всего окна. Так нельзя, и вот почему.
Нормированная энтропия (5-6) при частичной сумме равна

```
S = E_core/S_g + ln S_g = H_core + (1 − E_core/S_g)·ln S_g
```

где `H_core` — настоящая энтропия сердцевины, а второй член — штраф за
энергию, ушедшую из сердцевины в поля, с весом `ln S_g`. На срезе владельца
`S_g = 3,7·10^16`, `ln S_g = 38`: уход 1,8 % энергии в нулевые поля даёт
+0,70, тогда как весь выигрыш от фокусировки блока — около 0,1. Замер на
блоке с постройками при ЗАВЕДОМО внесённой ошибке и её точной поправке:

| критерий | S при истинной поправке |
|---|---:|
| с маской сердцевины | **+0,44** — истина «хуже нуля» |
| без маски, весь буфер | −0,09 — истина в минимуме |
| полный кадр, те же строки | −0,14 |

Тот же штраф сидит в производных, как только энергия пересекает границу,
и Ньютон борется с утечкой вместо фокусировки. Критерий, зависящий от
масштаба данных, неверен по построению: энтропия распределения от масштаба
зависеть не может. На подделке этого не было видно — там выигрыш от
фокусировки в разы больше штрафа.

Теперь (5-5), (5-13), (5-19) считаются по всему буферу блока, включая
нулевые поля, и Парсеваль соблюдается точно. Перехлёст при этом голосовал
бы — но его доля равна нулю по замеру выше, так что голосовать некому.
Границы сердцевины остались для укладки в этапе D. Стенд после правки:
приёмка §10 выполнена вся, остаток по книжной нарезке 0,628 против 0,623
рад, контраст 32,85 против 32,78 — в пределах шума стенда.

**Перехлёст ВОЗВРАЩЁН, 0,25 — замером на настоящей записи.** Стенд стыков
блоков не видит: остаток фазы меряется по бинам, а контраст тонет в
разбросе сцен. На срезе владельца при поправке 10…25 рад размаха нарезка
без перехлёста оставляет на каждом стыке тёмную полосу: поправка — свёртка
по азимуту на ±20 отсчётов, и крайним строкам сердцевины не хватает
соседей, которых в окне нет. Замер — средняя |g| по строкам стыков к
средней по остальным строкам (1,00 — стыка не видно) и линейка по восьми
целям:

| перехлёст | стык/фон | −3 дБ | −20 дБ | ISLR, дБ | глазом |
|---:|---:|---:|---:|---:|---|
| до счёта | 0,997 | 1,80 | 7,24 | −1,46 | |
| 0,00 | **0,724** | 1,30 | 4,11 | −4,10 | полосы с периодом блока |
| **0,25 — взято** | 0,993 | **1,10** | 4,53 | **−5,19** | полос нет |

Голоса перехлёст теперь имеет — маска убрана, — и это допустимо: начальная
фаза у соседей общая (решение №10), а на 15 м соседняя земля ошибку
движения не меняет. Цена: L = 2·m_b вместо 1,5·m_b.

## Решение реализации №7: пустые доплеровские бины

**Книга молча считает доплеровскую ось занятой целиком.** На реальной записи
это неверно, и вот арифметика: полоса доплера `B_a = v/r_a`, частота
повторения `PRF = v/шаг`, значит занятая доля равна `шаг/r_a` — отношению
ШАГА картинки к РАЗРЕШЕНИЮ. На записи владельца шаг 0,0464 м при разрешении
0,4 м: занято **11,6 %** оси, то есть 39 бинов из 330 в блоке. Остальные 291
несут только шум приёмника.

**Что они делали.** `E''` (5-19) в пустом бине мал, Ньютон (5-8) выдаёт
огромный шаг, шаг упирается в предел `STEP_MAX_RAD`, и критерий (5-9) встаёт
РОВНО на `2|sin(1/2)| = 0,9589` и держится там вечно. Это тот же предельный
цикл, что был при пределе `π`, только теперь его устраивают пустые бины.
Замер (M = 330, занято 39):

```
как есть        40 итераций, критерий 0,959 все 40, НЕ сошлось,
                |phi| вне полосы доходит до 5,48 рад — чистый шум
только полоса    7 итераций, критерий 0,959 -> 0,100, СОШЛОСЬ
```

Так же выглядел и первый прогон на настоящей записи: 7 блоков из 9 не
сошлись, упёршись в предел итераций.

**Правило.** Занятым считается бин, мощность которого выше МЕДИАНЫ профиля
`p(k) = Σ_n |h(k,n)|²` в 10 раз. Медиана — это уровень шума, пока пустых
бинов больше половины. Порог выбран не на глаз: отношение `max/медиана`
разводит два случая на два порядка, и 10 стоит посреди пустоты между ними.

| | max / медиана |
|---|---:|
| стенд, ось занята целиком | points 1,0 · +фон 1,2 · только фон 1,4 |
| запись, занято 11,6 % | шум 0,10 → 102 · 0,03 → 1106 · 0,01 → 9866 |

Точечная цель даёт `|h(k)|` ПОСТОЯННУЮ по доплеру, поэтому у занятой целиком
оси профиль плоский, и никакая яркость сцены его не вспучит. Правило
отключается само в двух случаях: живых меньше восьми (это выброс, а не
полоса — например узкополосная помеха) и живых больше половины оси (медиана
попала в сигнал, разделять нечего).

**Что это даёт и чего не даёт.** На стенде с ограниченной полосой правило
находит её ТОЧНО — 82 из 82 и 38 из 38 занятых бинов — и снимает предельный
цикл: (5-9) прибит 40 итераций из 40 без правила и 0 с ним. Но остаточную
ошибку фазы оно **не улучшает**: она упирается в то, что описано выше, в
разделе «Главное, что нужно знать». Решение №7 чинит сходимость и стоимость,
а не попадание в истину.

Геометрия в правиле не участвует: этап C по-прежнему не читает ни одного
параметра движения (§2.1). Занятость меряется по данным, а геометрия её лишь
предсказывает — `bench/run_real.py` печатает оба числа рядом, и они обязаны
сойтись.

## Решение реализации №8: возвращается лучшая точка, а не последняя

**Ньютон (5-8) с диагональным гессианом спуска не гарантирует.** Направление
`−E'/E''` построено без перекрёстных членов — это «среднеполевое»
приближение, и шаг может пройти мимо минимума. Книга сторожа не ставит. Но
она и не говорит, КАКУЮ точку считать ответом: сказано лишь, когда
остановиться (5-9).

Замер на стенде, 72 прогона (три сцены × 12 зёрен × два порога):

```
итераций всего 2222, энтропию УВЕЛИЧИЛИ 342 — 15,4 %
прогонов, где итог хуже лучшей посещённой точки: 24 из 72
```

Что даёт возврат лучшей точки (медиана остатка по 12 сценам):

| сцена | mu | последняя | лучшая | лучше в |
|---|---:|---:|---:|---:|
| points | 0,03 | 0,286 | 0,274 | 8/12 |
| points_and_clutter | 0,03 | 0,357 | 0,345 | 9/12 |
| clutter_only | 0,03 | 1,573 | 1,511 | 9/12 |

Выигрыш скромный, 3–4 %, но он **бесплатный**: лишних БПФ нет, только копия
массива фазы, и по собственной мере алгоритма (5-6) ответ не может стать
хуже — это свойство, а не замер.

**Второе, ради чего это сделано.** На реальной записи энтропия в двух блоках
из девяти за прогон ВЫРОСЛА: 12,3142 → 12,3769 и 11,7879 → 11,9368. Отчёт,
в котором минимизируемая величина растёт, выглядит сломанным, и отличить
настоящую беду от неудачного последнего шага в нём нельзя. С решением №8
«S после» не может превысить «S до» никогда — проверено на всех 72 прогонах.

История итераций при этом печатается как есть: рост внутри прогона виден,
скрывать его незачем.

## Решение реализации №10: этап B без ИНС — начальная фаза полиномом

Не из перечня задания; найдено на настоящей записи владельца, и это то,
из-за чего картинка не фокусировалась.

**Задача.** Книжный этап B строит φ⁽⁰⁾ из параметров движения. Без ИНС их
нет, и этап C шёл из нуля. На срезе владельца (6000×1335, 22 блока по
(5-20)) из нуля не выходит ничего: все блоки «сходятся» за 1–5 итераций с
падением энтропии 0,0001…0,02, а цели остаются шириной 6–13 элементов по
−20 дБ при норме около 2,8.

**Что это — нет ошибки или алгоритм слеп — решено пробой.** В те же данные
внесена заведомая квадратичная фаза, 8 рад на краю полосы. Ширина −20 дБ
выросла 7,24 → 9,53; этап C из нуля вернул 9,40 — снято 6 %. На подделке
та же машина снимала всё. Значит **алгоритм слеп именно на этой сцене**.

**Почему слеп, замером.** Шаг Ньютона (5-8) из нуля против истины по
блокам: по модулю 0,2…1,2 % истины, косинус от −0,6 до +0,6, в среднем
около нуля. Пофазный градиент (5-13) в блоке из 273×1335 отсчётов клаттера
тонет в шуме: у каждого бина свой случайный вклад от спекла, а общая для
всех бинов осмысленная часть за ним не видна. Критерий при этом верен —
скан энтропии блока вдоль истинной поправки даёт минимум у истины (после
снятия маски, см. поправку к №6). Слеп не критерий, а пофазный шаг.

**Правило.** Начальная фаза ищется как полином по энтропии **всей сцены**
(`stage_b_search.py`): несколько коэффициентов вместо сотен бинов, шум по
бинам усредняется, впадина энтропии по коэффициенту гладкая. Базис —
многочлены Лежандра второй и третьей степени по нормированной частоте `u`
(±1 на краю занятой полосы, 0 вне её): ошибка скорости и ускорения, то,
что даёт полёт. Четвёртая и пятая степени проверены и отброшены: они
опускают энтропию ещё на 0,005 из 0,040, но при заведомо квадратичной
внесённой ошибке коэффициент при P₄ менялся на 2,9 между чистыми и
испорченными данными — впадина по нему плоская, он ловит шум. Поиск:
грубая сетка 9×9 по двум коэффициентам (шаг 4 рад), затем покоординатное
уточнение с делением шага, всего около 130 БПФ сцены против 8800 у этапа
C. Найденный полином идёт в каждый блок на его доплеровскую сетку через
`truth_on_block_grid` — ровно на место, которое книга отводит этапу B.
Формулы этапа C не тронуты.

**Замер на настоящей записи, поправка одним полиномом (до этапа C):**

| | −3 дБ | −20 дБ | ISLR, дБ |
|---|---:|---:|---:|
| до | 1,80 | 7,25 | −1,46 |
| после полинома | 1,24…1,33 | 4,7…5,7 | −3,5…−3,7 |

(медианы по восьми самым ярким одиночным целям, ширины в элементах
разрешения; норма сфокусированной цели −3 дБ ≈ 0,9…1,3, −20 дБ ≈ 2,8).
Полином с более глубоким минимумом энтропии даёт и более узкие цели — то
есть минимум энтропии сцены отвечает резкости, и это проверка, а не вера.

**Чего он не снимает.** По пробе с внесённой ошибкой этап B без ИНС снимает
40 % внесённого по СКО в полосе: квадратичную часть — на 86 %, а
остальное — разница в кубической и та часть, что полиномом не описывается.
Остаток отдаётся этапу C, который из хорошей точки уже работает — решение
№8 гарантирует, что хуже полинома он не сделает.

Три дополнения к решению №10, все замерены:

* **масштаб по дальности** `(R/R_B0)^(d−1)`: при ошибке скорости остаток
  при данной доплеровской частоте растёт с дальностью линейно, при ошибке
  ускорения — квадратично (вывод в `RANGE_POWER_OFFSET`). На срезе в
  1700 м по дальности без этого поправка по краям врёт на ±25 %;
* **широкий предварительный скан** квадратичной ±320 рад с шагом 8 по
  каждому четвёртому стробу — сетка 9×9 с шагом 4 сотен радиан не достаёт.
  Проба: внесено −140·(R/R_B0)·u² (размаз ±21 м), найдено +134,2 при
  ожидаемых +136; линейка −20 дБ 37,3 → 5,04, ISLR +7,8 → −5,4 — как у
  чистых данных (4,53 / −5,19);
* **сегменты по азимуту** — своя поправка на каждый участок полосы, два
  прохода (`correct_segments`). Включается само на срезах длиннее 4096
  строк; `run_real.py` печатает профиль по сегментам с пометками «полоса
  урезана» и «ошибка N % фазы апертуры — опорная функция продукта».
  Устройство — итог четырёх замеров, каждый из которых отменил
  предыдущую версию:

  1. **Поиск — по кольцевому окну, без нулевых полей.** С полями 0,5 поиск
     на крае кадра возвращал ноль там, где ручной скан находил +510 и
     +690 рад: при размазе ±1400…1800 строк поправка выталкивает энергию
     краёв окна в поля, энтропия буфера растёт и прячет впадину
     (`SEGMENT_SEARCH_PAD_FRACTION`).
  2. **Применение — перекрытие с сохранением, одна поправка на плитку**
     (`apply_segments`, `TILE_ROWS` = 128, окно 4096). Первая версия
     склеивала сегменты окнами sin², и в одной строке складывались четыре
     версии цели, исправленные фазами 125, 150, 174 и 263 рад: цели в
     строках 1368…1798 стали шире, 8,0 → 20 элементов, при 4,0 от одного
     полинома на сцену. Комплексные картинки с разной остаточной фазой
     интерферируют; складывать их нельзя.
  3. **Первый проход — только квадратичная**, окна 2048 строк, шаг 512,
     скан ±1200 рад. Совместная подгонка с кубической завышала
     квадратичную (150/174 против 130/160 без неё) и давала кубическую
     −24…−168, которая одна ухудшала те же цели с 8,0 до 12,2 элемента.
  4. **Второй проход — окна 1024, шаг 256, квадратичная ±150 и кубическая
     ±60**: остаток после первого прохода — десятки радиан, и короткое окно
     его накрывает, видя профиль вдвое мельче (окна 1024 и 512 на крае
     кадра дали тот же профиль, что 2048).

  Проба с растущей вдоль азимута 100→500 рад: −20 дБ 47,9 → **5,05**,
  ISLR +10,2 → −3,7 при 4,53 / −5,2 у чистых данных той же обработкой.


**Задача.** §8 документа: множитель нормировки прямого и обратного ПФ в книге
не указан; на положение минимума не влияет, пока согласован между (5-3) и
(5-14), но входит в абсолютное значение `E''`, а значит в длину шага (5-8).

**Правило.** Пара множителей **взаимно обратна**: (5-3) несёт `α`, (5-14)
несёт `β = 1/α`. Принято `α = 1`, то есть обе суммы считаются ровно так, как
написаны в книге, без множителей. Пара живёт в `backend.py` и больше нигде.

**Что тут уточняется против документа.** «Согласован» из §8 — это именно
`α·β = 1`, и тогда утверждение оказывается сильнее, чем сказано в книге:
не только положение минимума, но и **сами `E'` и `E''`, а значит и длина
шага, не зависят от `α` вовсе**. Причина видна из выкладки: при `α·β = 1`
лишний член `ln α²` входит в (5-13) чисто вещественным и под `Im` пропадает,
а в (5-19) появляется дважды с противоположными знаками и сокращается точно.

**Чем подтверждено.** Таблица в отчёте: `α` перебирается по
1, 1/M, 1/√M, M, 1234,5 — расхождение шага на уровне машинного нуля
(≤ 5·10⁻¹⁶). Для сравнения там же стоит **несогласованная** пара
(`α = 1/M`, `β = 1`, то есть просто `numpy.fft.ifft` и `numpy.fft.fft`):
она меняет шаг почти на 100 %. То есть оговорка книги верна, и цена ошибки
в ней — полностью другая траектория сходимости.

## Решение реализации №4: предел числа итераций

**Правило.** Предел — **40 итераций**.

**Откуда взято** (правило 14). Книга (§2.3 документа) обещает сходимость за
7–8 итераций на манёвренном носителе и там же прямо предупреждает, что на
ровном полёте с малым `φ⁽⁰⁾` сходимость **медленнее**. Предел взят оттуда с
пятикратным запасом: 5 × 8 = 40.

**Упереться в предел — это НЕ сходимость.** `BlockIterations.converged`
остаётся `False`, а `stop_reason` говорит это словами и называет последнее
значение критерия (5-9). Отчёт печатает и то, и другое.

**Порог останова `μ`.** По умолчанию в `stage_c_iterate.MU_DEFAULT` стоит
**книжное** `μ = 0,1` (§5.7 документа). Замер это число подтверждает: при
`μ = 0,1` останов наступает на 9-й итерации, то есть книжные «7–8» —
настоящее число, а не оценка. В опытах используется `μ = 1e-3`, и это тоже
выбор **по замеру**, а не по вкусу: развёртка по `μ` в отчёте показывает,
что ниже 1e-3 остаточная ошибка перестаёт улучшаться.

# Места, где документ допускает чтение

Четыре места, где документ не противоречив, но и не однозначен. Решения приняты
и проверяемы; названы здесь, чтобы владелец не искал их по коду.

**1. `k_10`, `k_20`, `k_30` нигде не выписаны.** Книга пользуется ими в
(5-27)/(5-28), но формул не даёт. Они восстановлены из того же разложения
хода дальности, производными которого являются (4-83)/(4-84):

```
R(t_a) = sqrt(R_B0² + 2A_1 t_a + A_2 t_a² + μ_3 t_a³)
k_10 = A_1/R_B0
k_20 = A_2/(2R_B0) − A_1²/(2R_B0³)
k_30 = μ_3/(2R_B0) − A_1A_2/(2R_B0³) + A_1³/(2R_B0⁵)
```

Восстановление **проверяемо и проверено**: численная производная `k_1` по
координате точки совпадает с напечатанным `Δk_1x` до 10⁻¹¹ относительной
разности; для `k_2` и `k_3` расхождение есть и названо числом в отчёте — оно
ровно того порядка, что отброшенные книгой члены высшего порядка по `A_1`.

**2. В какой точке берётся `ε` в (5-30).** Взята опорная точка
`(x_max, y_max)` — та же, что в знаменателе (5-29). Иначе множитель
`(D_x x + D_y y)` вошёл бы дважды. При таком чтении, если отбросить
неразъяснённый член `−(q−q_k)/2`, произведение `η·ε` сводится ровно к модели
фазы в центре блока, `(D_x x_qk + D_y y_qk) f_a²`, — то есть к тому, что
физически и ожидается.

**3. Как читается нарезка на блоки.** §3.3 документа говорит прямо: «блок
занимает `[−x_p, +x_p]` по азимуту и `[−y_p, +y_p]` по дальности», где
`x_p`, `y_p` — метры на местности (§1.3), а (5-22)/(5-23) переводят их в
отсчёты изображения. Значит **блок это участок сцены**, и режется изображение
по пикселям `m`, а не массив данных по доплеровским бинам `k`.

Длина преобразования (5-3) в блоке — вопрос отдельный, и книга отвечает на
него **дважды по-разному**. §4.5 и блок-схема §7 называют `φ⁰` «вектором
длины M», где `M` — размер сцены. §5, открывая этап C, объявляет: «далее
`M`, `N` — размеры блока, `h(k,n)` — его данные». В список §8 книги это
расхождение не попало — оно **седьмое**, найдено при разборе.

Взято второе, и вот почему. В (5-3) сумма идёт по `k = 1…M` с ядром
`e^{−j2πkm/M}`: это одна и та же `M`, длина суммы и есть длина
преобразования. Если §5 объявляет `M` размером блока, то и преобразование
берётся по блоку. Отсюда: плитка изображения возвращается в область
дальность-доплер обратным ПФ **длиной в блок**, вектор `φ` имеет столько же
отсчётов, и **энергия за границу блока выйти не может** — свёртка круговая,
всё, что уходит за край плитки, возвращается с другого её края.

Полоса доплера при этом не сужается. Сетка из `m_b` бинов накрывает ту же
полосу PRF, только реже, с шагом `PRF/m_b`. Поэтому ось частот для (5-27)
строится как `azimuth_frequency_axis(m_b, T_a, M)`: длина у блока, полоса у
радара.

**Здесь была исправлена собственная ошибка замера, и она стоит того, чтобы
быть названной.** Раньше в этом месте стояла таблица, объявлявшая блочное
преобразование негодным — якобы энтропия в истинной фазе выходила у него
хуже, чем при `φ = 0`. Замер был неверен: найденная блоком фаза сравнивалась
с **отрезком** истины. Но блок из `m_b` бинов накрывает всю полосу доплера,
а не её кусок, — его бину `j` отвечает частота `j/m_b` от полосы, а не `j`-й
бин апертуры. Истину надо **пересчитывать** на сетку блока
(`validate.truth_on_block_grid`), а не резать. С отрезком вместо истины
негодным выглядел бы любой способ.

Сравнение двух прочтений ведётся по **готовой картинке**
(`validate.image_sharpness`): у блочного и сценного преобразований разные
сетки, и остаток фазы у них прямо не сопоставим, а собранное изображение —
общий знаменатель. Все три числа не меняются при циклическом сдвиге, то есть
не штрафуют за линейную составляющую, к которой энтропия слепа (§7.2).

| способ | длина (5-3) | `S` (5-6) | контраст | пик | энергии вне блока |
|---|---|---:|---:|---:|---:|
| **блочное ПФ (как в §5)** | `m_b` блока | **4,560** | **34,81** | **100,4** | **0,0 %** |
| сценное ПФ | `M` сцены | 4,946 | 29,59 | 100,3 | 5,5 % |
| идеальная сцена | — | 4,164 | 37,57 | 101,2 | — |

Книжное прочтение лучше по всем числам сразу, и вдобавок дешевле: БПФ короче.
У сценного прочтения энергия блока уходит в занулённую область — на чужую
землю — и попадает в энтропию (5-5) этого блока; замерено 5,5 %.

**4. «Линейная по k» в §7.2 задания.** Номер бина берётся
**центрированным** (`k̃ = −M/2 … M/2−1`), потому что ядро (5-3) периодично
по `k` и бины `k` и `k−M` — один и тот же бин. Разница не косметическая: при
чётной (квадратичной) вносимой ошибке оба представления дают одно и то же, а
при нечётной (кубической) снятие линии по натуральному `k = 0…M−1`
показывает остаток 1,58 рад там, где настоящий остаток 0,046 рад. Замер — в
отчёте.

Там же измерено и само утверждение §7.2: энтропия слепа к постоянной фазе
**точно**, а к линейной по `k` — **лишь при сдвиге на целое число отсчётов**;
при дробном сдвиге она меняется. Снятие полинома первой степени остаётся
правильной и притом консервативной (в пользу алгоритма) поправкой.

Наконец, сравнение ведётся **по модулю 2π**: фаза определена с точностью до
2π (§5.7 документа), и бин, где оценка отличается от истины ровно на 2π,
изображению тождествен. Обычное СКО объявило бы его ошибкой в 6,28 рад.

Первое, что новый стенд показал, — что доли в решении №6 были подобраны

Ниже — как было, для памяти.

**1а. Как это выглядело.** `synthetic.phase_error` вносит
ОДИН вектор на всю сцену, и `range_doppler_from_scene` домножает им все

  неизменчивой ошибке любой размер блока годится одинаково;

Это самый крупный пробел. Чтобы его закрыть, `phase_error` должна возвращать
не вектор длины `M`, а функцию от координат на местности, и

**2. ЧАСТИЧНО ЗАКРЫТО. Запущено на настоящей записи.** Срез 2964x1800 с

Осталось непроверенным: как выбирать сетку блоков на записи (сейчас по

# Допущение книги о скорости — для владельца

Книга берёт скорость **одним числом на всю апертуру**: `A_1`, `A_2`, `μ_3`
из §2.1 документа — объёмные постоянные, и книга это оговаривает прямо
(«обычно при обработке изображения эти параметры считают фиксированными
постоянными»).

**Это противоречит правилу проекта «скорость не одна, а матрица».**

В этом задании допущение книги **сохранено и менять его нельзя**: иначе это
уже не MN-MEA. Записано здесь, чтобы при встраивании вопрос всплыл, а не
потерялся.

Что при этом важно знать:

* допущение касается **только этапов A и B**. Этап C не использует ни одного
  параметра движения — в (5-3),(5-13),(5-14),(5-19),(5-8),(5-9) входят
  только `h(k,n)` и текущий `φ_k`. Поэтому именно этап C проверяется
  отдельно и первым, и именно он переносится во встраивание без вопросов;
* ИНС алгоритму не нужна ни на одном этапе;
* книжное число блоков `q` — **оценка снизу** (§2.3 документа): размер блока
  по (5-20) учитывает только номинальную изменчивость, а неучтённое движение
  добавляет свою.

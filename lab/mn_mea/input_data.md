Проверить подготовленное:

```python
import inputs

for n in замечания:
    print(n)
```

---

## 1. Обязательное: массив `h`

Единственное, без чего алгоритм не запустится.

| | требование |
|---|---|
| форма | `(M, N)` — **первый индекс доплер, второй дальность** |
| тип | комплексный: `complex64` или `complex128` |
| `M` | число импульсов в апертуре, не меньше 16 |
| `N` | число стробов дальности, не меньше 1 |
| раскладка по `k` | как у `numpy.fft`: нулевая частота в индексе 0, положительные дальше, отрицательные с конца |
| значения | ни одного `NaN`, ни одной бесконечности |

**Что это за данные.** Дальность-доплер ПОСЛЕ сжатия по дальности,
исправления миграции по дальности и прямого ПФ по азимуту — вход блок-схемы
§7 документа. Ни сжатия, ни миграции алгоритм не делает.

**Чего можно не делать:**

* нормировать — энтропия (5-6) от общего множителя не зависит;
* доводить `M` до степени двойки — проверено на `M = 250` и `M = 251`;
* вычитать среднее, выравнивать уровни.

**Если данные пришли центрированными** по доплеру (нулевая частота в
середине оси) — один вызов:

```python
h = numpy.fft.ifftshift(h, axes=0)
```

`inputs.check_data` это заметит и скажет, но только если сигнал занимает не
всю полосу. Если занимает — проверка промолчит, следите сами.

## 2. Для разбиения на блоки: `Geometry`, 14 чисел и одно необязательное

Нужно **только** этапам A и B. Этапы C и D геометрию не читают вовсе.

| поле | что | единицы | откуда |
|---|---|---|---|
| `v_x0, v_y0, v_z0` | скорость носителя | м/с | ИНС/GPS на середину апертуры |
| `a_x, a_y, a_z` | ускорение носителя | м/с² | оттуда же |
| `x_m, y_m, z_m` | центр сцены относительно носителя | м | геопривязка |
| `R_B0` | наклонная дальность до центра сцены | м | геометрия съёмки |
| `f_0` | несущая частота | Гц | паспорт станции |
| `r_a` | РАЗРЕШЕНИЕ по азимуту, ширина отклика | м | паспорт обработки |
| `r_b` | разрешение по дальности | **м на отсчёт** | паспорт обработки |
| `T_a` | время синтеза | с | паспорт обработки |
| `r_a_step` | ШАГ картинки по азимуту, необязательное | **м на отсчёт** | `v/PRF` |

**`r_a` и `r_a_step` — разные числа.** Разрешение — ширина отклика точечной
цели; шаг — расстояние между соседними отсчётами картинки. Совпадают они
только у критично дискретизованной картинки; на реальной записи шаг равен
`v/PRF`, а разрешение выходит шире из-за весового окна и запаса по полосе,
обычно в 1,2–1,5 раза.

Входят они в **разные формулы**:

* `r_a` → критерий (5-20) `|ΔR| ≤ r_a/2`, он про ширину отклика: остаточный
  ход дальности не должен выйти за половину отклика. Отсюда полуразмер блока
  в метрах `x_p`;
* `r_a_step` → перевод (5-22) `m_p = 2·x_p / шаг`, он про число отсчётов.

Одно число на обе роли ошибается в размере блока ровно во столько раз, во
сколько разрешение шире шага. Не задали `r_a_step` — берётся `r_a`.

Два условия, которые проверяются:

* `R_B0` обязан равняться `|(x_m, y_m, z_m)|` — это одна и та же точка;
* скорость не ноль, иначе (5-27)/(5-28) не определены.

Скорость и ускорение берутся **по одному числу на всю апертуру** — так
устроена книга. Берите значение на её середину.

**`lambda_` готовить не нужно.** Поле в `Geometry` есть, но алгоритм не
читает его ни разу: длина волны входит через `c / f_0`.

## 4. Если ИНС нет

**Коротко, по итогу на настоящей записи:** без ИНС этап B делается не по
(5-30), а поиском полинома по энтропии всей сцены — `stage_b_search.py`,
решение №10 в README. Из нуля этап C на записи слеп (замерено пробой:
снимает 6 % заведомо внесённой ошибки), с полиномом на входе цели сужаются
с 7,25 до ~5 элементов по −20 дБ. Ниже — история замеров на стенде, из-за
которых книжный этап B отключён.

Сначала важное о том, где скорость и ускорение использовались на стенде,
чтобы таблица ниже читалась верно.

**Использовались дважды.** Первое: **сетка блоков** во всех прогонах бралась
из (5-20), то есть прямо из `v` и `a` — `linearisation_coefficients` →
`block_half_sizes` → 6×2. Второе: на изменчивом стенде из них же строилась
**вносимая ошибка** — `D_x, D_y` по (5-27)/(5-28) и карта `s_map`.

Модуль `bench/synthetic.py` `Geometry` действительно не читает, но числа ему
передаёт `bench/validate.py`, а берёт их из геометрии. Так что «симуляция
геометрию не использует» — неверно, и эта оговорка здесь стоит намеренно.

Отсюда следствие для замера: сравнивать «сетку от ИНС» с «сеткой руками
6×2» бессмысленно — это одно и то же число. Ниже сетка перебрана
независимо.

**Замер.** Изменчивая ошибка, три сцены, `M = 256`, `N = 96`:

| сетка блоков | размер блока, отсч. | контраст | пик |
|---|---|---:|---:|
| от геометрии (5-20) + этап B | 43×48 | 33,80 | 99,8 |
| от геометрии (5-20), `φ⁰ = 0` | 43×48 | 34,24 | 100,5 |
| руками 2×1 | 128×96 | 28,54 | 99,4 |
| руками 4×2 | 64×48 | 33,86 | 100,1 |
| **руками 8×3** | 32×32 | **35,45** | 100,2 |
| **руками 12×4** | 22×24 | **35,49** | 100,4 |
| **руками 16×6** | 16×16 | **35,54** | 99,6 |
| руками 24×8 | 11×12 | 34,36 | 100,2 |

Читается так.

**Слишком крупно — плохо.** Блок в 128 отсчётов даёт 28,54: одна поправка на
пол-сцены не справляется с изменчивостью.

**Плато широкое.** Блоки в 32, 22 и 16 отсчётов дают 35,45 / 35,49 / 35,54 —
разница в пределах 0,1, то есть попасть в него легко.

**Слишком мелко — снова хуже.** Блок в 11 отсчётов даёт 34,36: в нём
остаётся мало энергии, и энтропии не за что зацепиться.

**(5-20) даёт не оптимум, а запас.** Её ответ — 43 отсчёта, контраст 34,24
против 35,5 на плато. И это на данных, изменчивость которых построена по
её же модели (5-27), то есть в самом выгодном для неё случае.

**Книжная начальная фаза (5-30) мешает:** 33,80 против 34,24 при `φ⁰ = 0`.
Причина замерена и описана в README — неразъяснённый член `−(q−q_k)/2` в
(5-29). Этап B можно не делать вовсе.

### Что делать без ИНС

1. Стартовать с `φ⁰ = 0`. Этап B пропускается целиком — он и с ИНС не
   помогает.
2. Сетку перебрать. Отправная точка — блок в **16–32 отсчёта по азимуту**;
   при `M = 256` это `M_k` от 8 до 16.
3. Сравнить контраст собранной картинки (`validate.image_sharpness`) на
   двух-трёх сетках. Плато широкое, попасть легко.

`Geometry` формально нужна `block_grid` как аргумент, но при `φ⁰ = 0` из неё
читаются только `r_a` и `r_b` — для координат центров блоков в метрах,
которые дальше никуда не идут. Нет и их — поставьте единицы.

**Оговорка.** Всё это измерено на изменчивости, построенной по модели книги
(5-27): квадратичная по `f_a`, линейная по координатам. Насколько настоящая
изменчивость на вашей съёмке ей отвечает — неизвестно, и проверить это можно
только на записи.

## 4а. Как нарезать запись на апертуры

**Запись — не апертура.** Кусок полёта в 17 секунд это не один кадр, а
десятки. Апертура задаётся нужным разрешением по азимуту:

```
T_a = λ·R / (2·v·r_a)          время синтеза
M   = PRF · T_a                импульсов в апертуре
B_a = v / r_a                  полоса доплера — от дальности НЕ зависит
```

Время растёт с дальностью потому, что скорость изменения доплера
`K_a = 2v²/(λR)` с дальностью падает. Полоса при этом всюду одна.

**`T_a` берётся по ДАЛЬНЕЙ кромке полосы.** Тогда `M = PRF·T_a` одинаково
для всех стробов и массив `h` выходит прямоугольным — другого алгоритм не
принимает. Ближняя кромка окажется переразрешена ровно в `R_дальн/R_ближн`
раз: апертура там длиннее, чем нужно.

Что с этим делать — на выбор:

* **оставить.** Ближние стробы выйдут резче дальних. Алгоритму безразлично;
* **выровнять.** Отфильтровать ближние стробы до той же полосы доплера. Но
  опустевшие бины дадут `E'' = 0`, сторож решения №2 их заморозит, и фаза в
  них не определится. Работать будет, а остаточную ошибку надо мерить только
  по занятым бинам.

### Считается функцией

```python
import inputs
план = inputs.aperture_plan(
    wavelength_m=0.03, range_near_m=1700, range_far_m=3700,
    speed_ms=75.0, prf_hz=1000.0,
    azimuth_resolution_m=1.0, record_seconds=17.0,
    overlap=0.0,            # 0.5 для непрерывной полосы
)
```

Пример для полосы 1700…3700 м и записи 17 с. **Числа `λ`, `v`, `PRF` здесь
взяты правдоподобные — подставьте свои:**

| нужное `r_a`, м | `T_a`, с | `M`, имп. | кадров встык | с перекрытием 50 % | `r_a` на 1700 м | сетка `M_k` |
|---:|---:|---:|---:|---:|---:|---|
| 0,3 | 2,47 | 2467 | 6 | 12 | 0,138 | 78…155 |
| 0,5 | 1,48 | 1480 | 11 | 21 | 0,230 | 47…93 |
| 1,0 | 0,74 | 740 | 22 | 44 | 0,459 | 24…47 |
| 2,0 | 0,37 | 370 | 45 | 90 | 0,919 | 12…24 |
| 3,0 | 0,25 | 247 | 68 | 136 | 1,378 | 8…16 |

Ближняя кромка переразрешена в **2,18 раза** при любом `r_a` — это просто
`3700/1700`.

### Порядок работы

```
запись 17 с
  └─ нарезать на апертуры по T_a (встык или с перекрытием 50 %)
       └─ для каждой: сжатие + миграция + ПФ азимут  →  h(k,n)
            └─ нарезать на блоки: M_k из колонки «сетка»
                 └─ этап C: iterate_block, phi0 = 0
                 └─ этап D: remove_image_shift, block_image, assemble
```

Автофокус стоит ВНУТРИ цикла по апертурам. Каждый кадр фокусируется сам по
себе: своя фазовая ошибка, своё разбиение, свой ответ.

## 5. Чего НЕ нужно

| | почему |
|---|---|
| истинная фазовая ошибка | на записи её никто не знает — она и есть искомое |
| опорная сфокусированная картинка | не с чем сравнивать и не нужно |
| разметка целей | алгоритм их не ищет |
| ИНС на каждый импульс | книга берёт одно число на апертуру |
| `matplotlib` | нужен только стенду, не алгоритму |

Всё перечисленное есть **только на стенде** (`bench/`), и потому стенд лежит
отдельно от `algorithm/`.

## 6. Наименьший рабочий пример

```python
import sys
sys.path.insert(0, "algorithm")

import numpy as np
from backend import get_backend
import inputs
import stage_c_iterate as C
import stage_d_assemble as D

h = ...                       # ваш массив (M, N), комплексный
assert not inputs.check_data(h), inputs.check_data(h)

backend = get_backend("auto")          # видеокарта, если она есть и РАБОТАЕТ
h_dev = backend.asarray(h)
M, N = h.shape

result = C.iterate_block(backend, h_dev, np.zeros(M), mu=1e-3)
phi = D.remove_image_shift(backend, result.phi)        # решение №5

print("сошлось:", result.converged, "за", result.n_iterations, "итераций")
print("энтропия:", result.normalised_entropy_history[0],
      "->", result.normalised_entropy_final)
```

Это один блок на всю сцену, без геометрии. Для разбиения добавьте `Geometry`,
`stage_a_blocks.block_grid` и цикл по блокам — как в
`bench/validate.experiment_full_run`.

## 7. Готовый прогон на записи

Всё перечисленное уже собрано в паре скриптов. `bench/prepare_slice_rda.py`
делает срез из записи: один аргумент — путь к файлу этапа `az`
(`*_rda@*.h5`), остальное — скорость и паспорт — он находит сам по
идентификатору источника; нужен `h5py`. `bench/run_real.py` этот срез
считает; он ждёт каталог с двумя файлами:

```
mn_mea_srez/
    h_srez.npy    массив (M, N), комплексный — §1
    meta.json     паспорт: блок "geometry" (§2) плюс два числа по азимуту,
                  "r_a_razreshenie" и "r_a_shag"
```

```
python3 bench/run_real.py путь/к/mn_mea_srez          # сетка блоков по (5-20)
python3 bench/run_real.py путь/к/mn_mea_srez 8x1      # сетка рукой
```

Делает по порядку: читает срез, собирает `Geometry` (разрешение и шаг
разводит по своим полям), гоняет `inputs.check_inputs`, печатает
`derived_numbers`, считает блоки от нулевой начальной фазы, собирает картинку
и кладёт рядом `mn_mea_do_posle.png` — до и после в одном поле.

Если в паспорте есть раздел `ozhidaemaya_narezka` с ожидаемым `m_p_pravilnyy`
и `N_k_ozhidaemoe`, прогон сличает с ним свою нарезку и печатает «сходится»
или «НЕ СХОДИТСЯ». На записи это **единственная объективная сверка**: истины
по фазе нет, энтропия — цель алгоритма, а не проверка, независимо смотрят
только контраст и глаза.
